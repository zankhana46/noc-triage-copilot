## 1. Goal

Build an AI copilot for a telecom Network Operations Center (NOC). Given a burst of network alarms, it should:

1. Correlate related alarms into a single incident.
2. Use the network topology to localize the **root-cause node** and identify the **root-cause type**.
3. Retrieve the relevant runbook and produce grounded, step-by-step remediation.
4. Explain its reasoning with citations to alarms, topology paths, and runbook sections.

The project must show four things measurably: multi-agent orchestration (LangGraph), knowledge-graph RAG (Neo4j plus hybrid retrieval), a fine-tuned small model (QLoRA) compared against a large API model, and low-latency serving (vLLM) with benchmarks.

All data is **synthetic**, generated by a simulator with planted ground truth. That ground truth is what makes the evaluation trustworthy.

## 4. Phase 1 — Synthetic data simulator

### 4.1 Topology

Generate a realistic hierarchical mobile network, configurable in `simulator.yaml` (default about 300–500 nodes):

- **Core:** AMF/MME, UPF/SGW, a few core routers
- **Aggregation routers**, each connected to several **pre-aggregation routers**
- **Cell site routers (CSR)**, each serving one **site**
- Each site has a **gNodeB/eNodeB**, 3 **cells** (sectors), a **power system** (rectifier + battery), and a **sync source** (GPS/PTP)
- **Links** between routers with attributes: type (fiber/microwave), capacity, a redundant-path flag

Node properties: `id`, `type`, `region`, `vendor` (2–3 fictional vendors), `site_id`, `lat`, `lon`.
Export to `data/topology/` as CSV and load into Neo4j.

### 4.2 Failure scenarios

Implement at least 8 failure types. Each one injects a root cause at a node and **propagates realistic downstream alarms through the topology**:

| Root cause | Downstream effect |
|---|---|
| Fiber cut on aggregation link | Link down, then all downstream sites without redundancy raise backhaul/S1/NG failures and cell outages |
| Site power failure | Mains failure, then battery low after a delay, then site down and cell outages |
| Router hardware fault | Card failure, link flaps, then downstream degradation |
| Sync loss (GPS/PTP) | Sync alarm, then handover failures and throughput degradation in affected cells |
| Microwave link degradation (weather) | High BER, then intermittent packet loss and latency alarms |
| Cell congestion | High PRB utilization, then RRC setup failures and throughput drop |
| High temperature / cooling failure | Temperature alarm, then fan failure, then possible equipment shutdown |
| Core element overload | Elevated signalling latency, then attach/registration failures across many sites |

Alarm schema: `alarm_id`, `timestamp`, `node_id`, `alarm_type`, `severity` (critical/major/minor/warning), `vendor_code`, `message` (free text in vendor-specific styles), `incident_id` (ground truth, hidden from the copilot).

Realism requirements:

- **Noise:** unrelated background alarms, flapping alarms, and duplicates mixed into every time window.
- **Timing jitter** on propagated alarms.
- **Vendor-specific message templates.** Optionally use an LLM to paraphrase templates for variety, with outputs cached so generation is reproducible.
- Some incidents should overlap in time.

### 4.3 Runbooks

Generate one runbook per failure type, plus 2–3 vendor-specific variants, as Markdown files with consistent sections: *Symptoms, Probable causes, Diagnostic steps, Remediation, Escalation*. Use an LLM to draft them from a structured outline, then save them to disk so they're fixed.

### 4.4 Incident bundles (evaluation and training units)

Each incident bundle contains the alarm window shown to the copilot plus hidden ground truth: `root_cause_node`, `root_cause_type`, `affected_nodes`, and the correct runbook ID.

Generate about 1,000 bundles. **Split by random seed and topology region** into `train` (for fine-tuning), `dev`, and `test`, so that no test incident shares a root-cause node with any training incident.

### Phase 1 acceptance

- `scripts/01_generate_data.py` produces all data from `configs/simulator.yaml`.
- `docker compose up neo4j` starts Neo4j, and `scripts/01_load_graph.py` loads the topology.
- Tests confirm that propagation follows real topology paths and that redundant links prevent downstream outages.
- A data summary (counts per failure type, noise ratio, split sizes) is written to `results/data_summary.json`.

## 5. Phase 2 — Retrieval and graph tools

### 5.1 Runbook retrieval

Chunk runbooks by section. Implement hybrid retrieval: BM25 plus dense embeddings (Sentence-Transformers), merged with reciprocal rank fusion, then reranked with a cross-encoder. Make the retrieval mode configurable (`bm25`, `dense`, `hybrid`, `hybrid+rerank`) so it can be ablated.

### 5.2 Graph tools (used by agents)

Write safe, parameterized Cypher tools:

- `get_node(node_id)`
- `get_upstream_path(node_id)`: path from a node to the core
- `get_downstream(node_id)`: everything served by a node
- `find_common_ancestor(node_ids)`: lowest shared upstream node for a set of alarming nodes (the key RCA signal)
- `get_redundancy(node_id)`
- `text_to_cypher(question)`: LLM-generated **read-only** Cypher, validated (reject any write clauses) before execution

### Phase 2 acceptance

- Unit tests for every graph tool against a small fixture topology.
- `results/retrieval_eval.json`: recall@k and MRR for each retrieval mode, on queries built from incident bundles with known correct runbooks.

## 6. Phase 3 — LangGraph multi-agent copilot (using API model)

### 6.1 Graph design

A shared typed state flows through these nodes:

1. **Alarm Correlator:** groups the alarm window into candidate incidents (deduplication, time clustering, topology proximity), filters noise.
2. **Topology Analyst:** calls graph tools, especially `find_common_ancestor`, to propose ranked root-cause node candidates with evidence paths.
3. **Diagnostician:** decides the root-cause type from alarm patterns plus topology evidence; outputs top-3 hypotheses with confidence.
4. **Runbook Retriever:** retrieves runbook sections for the top hypothesis (and vendor).
5. **Remediation Writer:** produces the final incident report, grounded only in retrieved runbook text and tool outputs, with citations.
6. **Supervisor/router:** routes conditionally. If the Diagnostician's confidence is low, loop back to the Topology Analyst for more evidence (cap the number of loops).

Final output is structured JSON (validated with Pydantic): `incident_summary`, `root_cause_node`, `root_cause_type`, `top3_hypotheses`, `affected_nodes`, `remediation_steps`, `citations`, `confidence`.

### 6.2 Interfaces

- FastAPI endpoint `POST /triage` accepts an alarm window and returns the report.
- Streamlit UI: paste or select an incident, view the agent trace, topology path, and report.
- Log each run (latency, tokens, tool calls) to MLflow.

### 6.3 Evaluation (`scripts/03_evaluate.py`)

Run on the **test split** and record in `results/eval_<model>.json`:

- **RCA type accuracy:** top-1 and top-3
- **Root-node localization accuracy:** exact match, and within one hop
- **Affected-node F1**
- **RAGAS:** faithfulness, answer relevancy, context precision, context recall
- **Latency:** p50/p95 per incident; **cost per incident** for API models

Ablations, each saved to results:

- No graph tools (LLM sees alarms only) vs. full system
- Each retrieval mode from Phase 2

### Phase 3 acceptance

- End-to-end triage works via API and UI with the API model.
- Evaluation and ablation results saved. **This phase alone is a complete project.**

## 7. Phase 4 — QLoRA fine-tuning of a small model (GPU)

### 7.1 Dataset

Build from the **train split only**: input is an alarm window plus topology evidence (the same context the Diagnostician receives); target is the structured diagnosis JSON. Optionally add examples for the Remediation Writer. Save in chat format to `data/finetune/`.

### 7.2 Training

- Base: Qwen2.5-7B-Instruct (or Llama 3.1 8B Instruct), 4-bit QLoRA via `peft` + `trl` SFT.
- Hyperparameters in `configs/finetune.yaml`; log runs to MLflow.
- Fits on a single 24GB GPU. Provide `scripts/04_finetune.sh` that runs on RunPod or Colab with one command.
- Save LoRA adapters; also produce a merged model for vLLM.

### 7.3 Comparison

Re-run the Phase 3 evaluation with the LLM client pointed at:

1. API model (baseline)
2. Base small model (no fine-tuning)
3. Fine-tuned small model

### Phase 4 acceptance

- `results/eval_base_small.json` and `results/eval_finetuned_small.json` exist.
- A comparison table is generated automatically from the results files.
